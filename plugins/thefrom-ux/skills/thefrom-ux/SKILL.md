# thefrom-ux — 더프롬 UX 파이프라인 실행기 (v0.4.1 · 방법론 v0.6)

이 스킬의 목적은 **좋은 디자인**이다. 구체적으로는 사용자가 익숙하게 쓰면서도 처음 보는 것처럼 느끼고, 더프롬 시니어가 포트폴리오에 올릴 수 있는 수준의 화면이다. 방법론은 거기에 도달하기 위한 수단이다.

> **관성은 구조에서 지키고, 새로움은 해석에서 만든다.** (core.md §6.1)

## 0. 먼저 알아둘 것 — 이 스킬이 실패하는 방식

파일럿 1회차에서 이 스킬은 다음처럼 실패했다. 같은 실수를 되풀이하지 않도록 먼저 읽는다.

- **방법론을 결과물에 새겼다.** 결과 화면이 더프롬 로고의 3U·2U·1U 막대와 더프롬 브랜드 컬러를 닮았다. 1U는 치수가 어디서 왔는지를 설명하는 **보이지 않는 뼈대**다. 사용자가 1U를 알아볼 수 있다면 실패다.
  - 더프롬의 철학·형상·컬러는 **판단의 방법**이지 클라이언트 결과물의 소재가 아니다(core.md §1.1, §2.2.4, N7).
- **결과가 도표처럼 보였다.** 해석은 새로웠지만 위계·타이포·강조가 약해서, 주인공이어야 할 화면이 정보 그래픽처럼 읽혔다.
- **사용자가 얻는 것이 없었다.** "한 층만 다시 쌓기" 같은 새 작동을 만들었지만, 그것이 사용자의 어떤 동기에 답하는지 근거가 없었다.
- **노력이 문서와 증거 절차에 쏠렸다.** 문서를 쓰느라 시안을 다듬을 시간이 없었다.

파일럿 2회차에서는 이렇게 실패했다.

- **컨셉 아이디어에 치우쳤다.** 메타포("인물 기사")가 화면의 형식까지 정했다. 글은 좋았지만 사용자가 얻는 것이 **보이지** 않았다.
- **컨셉을 판정받지 않고 완성 시안까지 갔다.** 컨셉이 틀렸다면 그 비용은 전부 버려진다.
- **A/B가 같은 방향의 변주였다.** 두 안을 비교해도 무엇이 옳은지 드러나지 않았다.

그래서 v0.2는 세 가지를 바꿨다.

- 메타포와 별도로 **효익 시각화**를 설계한다. 메타포는 톤만 정하고, 형식은 사용자 과업이 정한다.
- 러프 1장으로 **C 게이트(컨셉 판정)**를 먼저 받는다.
- A/B를 **시스템 주도(대조군) / 경험 주도(본안)**로 나눈다.

그래서 **판단이 부딪히면 사용자 경험과 조형 완성도가 방법론의 형식보다 앞선다**(core.md §6.7).

| 부딪히는 것 | 이렇게 한다 |
|---|---|
| 1U 규칙이 미감을 해친다 | 1U 값을 바꾼다 |
| 정렬 규칙이 위계를 해친다 | 규칙을 벗어나고 근거를 적는다 |
| 메타포를 옮겼더니 화면이 나빠진다 | 메타포를 의심한다 |

**시간 배분**: 전체 노력의 절반 이상을 **시안과 크리틱 루프**에 쓴다. S 문서는 표 중심으로 짧게 쓴다.

## 1. 역할 — AI가 하는 일, 하지 않는 일

| 구분 | 대상 | AI가 하는 일 |
|---|---|---|
| **연산** | S0 초안, 사조 취사, 4축, 메타포 후보, 재해석 설계, 1U 파생, 시안 제작, G7 ①~⑦ 자기 비평 | 직접 수행하고 근거를 짧게 기록한다 |
| **증거** | 반대 대상 실례, 통상적 해석의 실례, G1 비교 레퍼런스 | 검색하거나 사용자에게 묻는다. **생성하지 않는다.** 없으면 `없음` |
| **판정** | **C 게이트(컨셉)**, G2 최종, G5 전체, G6 최종, G7 최종(⑧ 포트폴리오 기준) | **판정 키트**만 준비한다 |

**증거를 생성하지 않는 이유.** 반대 대상은 "이 업계는 다 이렇게 한다"는 **관찰**이어야 한다. 실례를 지어내면 상상 속의 적을 공격하는 조형(N1)이 가짜 근거로 통과한다.

- 모든 실례에는 출처(주소 또는 `사용자 제공`)를 붙인다.
- 인정하는 증거 유형과 **검색 중단 기준**(반대 대상 하나당 서로 다른 질의 5회)은 `qna.md` §3에 있다. 5회 안에 못 찾으면 멈추고 `없음`으로 적는다. 증거 찾기에 시안보다 많은 시간을 쓰지 않는다.

**예비 판정.** AI가 내린 G1·G3·G4·G6·G7 판정에는 `예비 판정`이라고 표기한다. 사람이 확정하기 전에는 출구를 통과한 것으로 기록하지 않는다.

## 2. 공통 루프

```
입력 → 연산 → 공백 감지 → QnA → 게이트
```

- **입력**: 이전 단계의 산출물 파일을 다시 읽는다.
- **공백**은 세 종류다. 정의형(프로젝트가 정할 값), 증거형(실재하는 것), 판정형(사람만 내릴 판정).
- **QnA**: `qna.md`에서 그 단계의 노드를 찾는다.
  - 도출할 수 있으면 묻지 않고 가정을 명시한다.
  - 답이 결과를 바꾸지 않으면 묻지 않는다.
  - **질문은 단계당 최대 3개를 한 번에 묶어서**, 가능하면 선택지로 묻는다.
  - 답과 가정은 해당 S 파일 끝에 기록한다.
- **사용자가 답할 수 없는 상황**(무인 실행, "알아서 해줘")에서는 종류별로 처리한다.
  - 정의형: 가정을 명시하고 진행한다.
  - 증거형: 검색하고, 그래도 없으면 `없음`으로 적는다.
  - 판정형: 예비 판정으로 보류하고 키트를 남긴다.
  - **브리프 게이트 ★1·★2·★3도 예외다.** 가정으로 채우지 않고 멈춘다.
  - **C 게이트는 예외다.** 사용자가 "끝까지 진행"을 명시하지 않았다면 **C 게이트에서 멈추고** 판정 키트를 넘긴다. 비용 원칙이 우선이다(core.md §6.8).
  - 이 경우에는 기록 개수에 제한이 없다.

## 3. 시작

1. **브리프 게이트 — "더프롬처럼 만들어줘"로는 시작하지 않는다.** 이 스킬은 감각을 흉내 내지 않고 판단을 계산한다. 판단의 재료는 브리프다. 요청을 받으면 제일 먼저 브리프의 **★ 필수 6항목**을 확인한다(`pipeline.md` S0 브리프 게이트, 양식은 `assets/brief-template.md`).

   | ★ | 항목 | 모호함의 예 |
   |---|---|---|
   | 1 | 무엇을 — 서비스·범위(화면)·핵심 흐름 | "성향 테스트 앱" |
   | 2 | 누구에게 — 타겟·상황·기기 | "MZ세대" |
   | 3 | 핵심 순간 — 주인공 화면·사용자가 얻고 싶은 것 | "결과가 예뻤으면" |
   | 4 | 브랜드 — 클라이언트 브랜드 또는 `없음` | 빈칸 |
   | 5 | 제약·재료 — 지킬 것·금지·이미 정해진 문항/데이터 | 빈칸 |
   | 6 | 성공 기준·깊이 — C 게이트까지 / 끝까지 | "잘 나오면" |

   - 항목을 읽고 **전혀 다른 화면이 두 가지 이상 가능하면** 모호한 것이다.
   - 비었거나 모호하면 **브리프 인터뷰**부터 한다. `Q-S0-01`·`02`·`07`(★1~3)을 먼저, 한 번에 최대 3개, 선택지로 묻는다. 사용자가 브리프를 새로 쓰겠다면 양식을 건넨다.
   - **★1·★2·★3 중 하나라도 비면 아무것도 만들지 않는다.** 무인 실행이어도 멈춘다. 이 셋을 가정으로 채우면 결과 전체가 가정이 된다.
   - ★4·★5·★6은 답이 없으면 가정으로 진행할 수 있다: ★4는 `없음`(더프롬 브랜드로 채우지 않음), ★6은 C 게이트까지.
   - 문항·데이터·기존 화면 같은 **재료가 있다면 받아서 쓴다.** 지어내지 않는다.
   - **브리프 작성 모드.** "브리프 쓰자", "브리프부터 같이 작성해줘", "브리프 양식 줘"처럼 브리프 자체를 요청하면, 이 대화 안에서 브리프를 함께 쓴다.
     1. 프로젝트명을 묻고 ★1부터 ★6까지 순서대로 인터뷰한다. 한 번에 최대 3개, 선택지와 `assets/brief-template.md`의 좋은 예를 곁들인다. 사용자가 한꺼번에 붙여 넣으면 그것부터 읽고 빈 칸만 묻는다.
     2. 답마다 위 표의 "모호함" 기준으로 확인하고, 모호하면 그 자리에서 한 번 더 좁힌다. 사용자가 "모름"이라고 하면 ★4는 `없음`, ★6은 C 게이트까지로 적고, ★1~3은 비워 둔 채 게이트에서 멈춘다.
     3. 끝나면 **브리프 .md 전문**을 `assets/brief-template.md`의 순서(★1~6, 7 비교, 8 판정자, 9 더 알려줄 것)로 출력한다. 맨 위에 `> 브리프 게이트: 통과 / 진행 가능 / 질문부터 / 멈춤`을 적는다. 파일을 만들 수 있는 환경이면 `브리프_<프로젝트명>_<YYYYMMDD>.md`로 저장한다. 사용자가 보관하거나 팀 `briefs/`에 올릴 수 있게 하기 위해서다.
     4. "이 브리프로 S0부터 진행할까요?"라고 묻고, 답을 받으면 같은 대화에서 바로 이어간다.
   - 사용자가 웹 편집기(`tools/brief-editor.html`)에서 넘긴 브리프는 이미 게이트 판정이 적혀 있다. 그래도 위 기준으로 다시 확인한다 — 편집기는 빈칸과 흔한 모호 표현만 잡는다.
2. **작업 폴더**: 사용자가 정하지 않으면 `<프로젝트명>-thefrom/`에 만든다.
   ```
   S0_정의.md  S1_여행기록.md  S2_믹스.md  S3_시스템.md  S4_판정.md  S5_실체화.md
   proto/  rough.html (C 게이트)  A.html  B.html  select.html (S3→S4)  final.html (S5)
   shots/  (크리틱 루프 캡처)
   kit/    C_컨셉판정.md  G2_메타포.md  G5_진행지.md  G6_판정.md  G7_판정.md
   ```
3. **`references/core.md`를 읽는다.** 특히 다음 절을 본다.
   - §1.1 철학의 층위
   - §2.2.4 1U 비가시
   - §4 airplane, §5 tunnel
   - §2.2.5 타입 스케일 단위
  - §6 게이트 전체: §6.4 G4, §6.5 G6, §6.6 G7, §6.7 우선순위, §6.8 비용 원칙
   - §7 하지 않는 것
   - 카탈로그는 통독하지 않고 단계가 지시하는 ID만 본다.

## 4. 단계

상세 형식(표 양식·예시·판정법)은 `references/pipeline.md`의 해당 절을 따른다. 아래는 순서와 놓치기 쉬운 지점이다.

### S0 · 정의 — `pipeline.md` S0 · Q-S0-*

- 컨셉을 한 문장으로 쓴다. 형식은 `[대상]이 [상황]에서 [무엇]을 [어떻게] 느끼게 한다`이다.
  - `[어떻게]`에는 **감정의 결**까지만 쓴다. 예: "서두르지 않는 속도로".
  - 화면 형상이나 결과 해석은 쓰지 않는다. 그것은 S2가 도출한다.
- **프로젝트 브랜드를 확인한다**(Q-S0-06). 없으면 "서비스 약속과 타겟에서 새로 정한다"로 가정한다. **더프롬 브랜드로 채우지 않는다.**
- G5 판정자는 사람만 정할 수 있다(Q-S0-04).
- 서비스 이름·가칭은 짓지 않는다. 이름이 결과 해석을 미리 정하기 때문이다. 필요하면 C 게이트 뒤에 짓는다.

### S1 · AIRPLANE — `catalog-ism.md` · Q-S1-*

- 사조 후보 3~5개를 고른다. 각 후보에 `가져올 것`(원리)과 `두고 올 것`을 프로젝트 맥락으로 적는다.
- **A3 점검**: `가져올 것` 문장에서 형태·색·서체 이름을 지운다. 지운 뒤에도 문장이 성립하면 원리이고, 사라지면 코스튬이다.
- 반대 대상을 쓸 거라면 실례 2건을 검색한다(검색 중단 기준 적용).

### S2 · TUNNEL — 스킬의 중심

`pipeline.md` S2 · `catalog-pattern.md`(PAT·VIZ·MOTION·STATE) · `catalog-form.md` B-9~B-13 · Q-S2-*

**순서**: 레이어 → 재해석 → **효익 시각화 + 러프** → **C 게이트** → A/B 시안 → 크리틱 루프. C 게이트 전에는 완성 시안을 만들지 않는다.

1. **레이어 3종**
   - ① **타겟**: 조형의 경계 조건을 정한다. 가독성 하한, 정보 밀도, 톤의 폭.
   - ② **클라이언트 브랜드**: 경쟁과 갈리는 지점을 찾는다.
   - ③ **UX**: `지킬 것 / 밀 것` 목록과 **화면별 동기·감정**을 적는다.
2. **패턴 재해석** — 핵심 화면마다 한다.
   - `PAT-*`와 지킬 가독성 → 통상적 해석(반대 대상 형식 + 실례, 없으면 `없음`) → 레이어에서 **메타포 하나** → 재해석(비주얼 · 작동 · 사용자가 얻는 것).
   - 더프롬의 철학·형상은 메타포의 출처가 될 수 없다.
3. **효익 시각화** — 재해석이 "무엇을 다르게 볼까"라면, 이것은 "**사용자가 무엇을 볼 수 있게 되는가**"다. 핵심 화면마다 다섯 칸을 적는다.

   | 칸 | 적는 것 |
   |---|---|
   | 과업 | 이해 · 비교 · 결정 · 공유 · 기록 중 무엇인가 |
   | 보이게 할 것 | 과업을 빠르게 하려면 무엇이 보여야 하는가 |
   | 형식 | `VIZ-*` 중에서 고른다. 문장이면 충분할 때는 `없음` |
   | 효익 지표 | 관찰 가능한 문장. 예: "설명 없이 3초 안에 가장 강한 축을 말한다" |
   | 메타포의 톤 | 형식이 아니라 결 |

   - **메타포는 시각화의 톤을 정하고, 형식은 과업이 정한다.** 메타포에 맞추느라 과업에 맞지 않는 형식을 고르지 않는다.
   - **러프 1장**: 주인공 화면을 와이어 수준(톤·색 없이 무엇이 어디에 얼마나 크게)으로 `proto/rough.html`에 만든다.
4. **C 게이트** — `kit/C_컨셉판정.md` 한 장을 만들어 사람에게 go / 수정 / 중단을 받는다(Q-S2-06).
   - 담는 것: 메타포 후보 2~3개와 권장안, 화면별 재해석 한 줄, 효익 시각화 표, 러프, 다음 단계 비용.
   - 묻는 것: 아름다운가가 아니라 **맞는 방향인가, 사용자에게 무엇을 주는가, 이 비용을 쓸 가치가 있는가**.
   - 무인 실행이면 "끝까지 진행"이 명시된 경우에만 권장안으로 넘어간다. 이때 C 게이트와 G2는 **예비**로 남고, 사람이 나중에 확정한다.
5. **A/B 시안** — 방법론을 어디에 두느냐의 두 갈래다.

   | | A · 시스템 주도 (대조군) | B · 경험 주도 (본안) |
   |---|---|---|
   | 방법론 | 1U·그리드·규칙이 형태를 결정한다 | 컴포넌트의 **구조·포인트·디테일** 안에 녹는다 |
   | 컴포넌트 | 규칙에 맞춰 새로 만든다 | 사용을 제약하지 않는다 |
   | 위험 | 작위적 단조로움 — 명분만 있고 효익 없는 **개살구** | 흔한 앱과 구분되지 않음 |
   | N7 | A도 지킨다 — 1U는 **규칙**으로 형태를 정할 뿐, 정사각형·막대·3/2/1 비례가 **모티프**로 보이면 안 된다 | 동일 |
   | 범위 | 핵심 화면 1~2개, 루프 1회 | 핵심 화면 전부, 루프 2회 이상 |

   - A는 이기라고 만드는 안이 아니다. 방법론이 명분으로만 작동하면 무엇이 되는지를 같은 컨셉 위에서 드러낸다.
   - B에서 방법론은 컴포넌트를 버리지 않고 다음 셋 중 하나 이상을 바꾸는 것으로 드러난다.
     - **구조**: 컴포넌트가 정보를 담는 방식
     - **포인트**: 시선이 머무는 단 한 곳
     - **디테일**: 상태·모션·타이포의 결
   - **명분·효익 표**: 설계 결정마다 명분(방법론 근거)과 효익(사용자가 얻는 것)을 나란히 적는다.
     - **효익 칸이 빈 결정은 개살구다.** B에서 나오면 삭제하고, A에서 나오면 기록으로 남긴다.
     - 선택은 **효익이 더 많고 강한 안**으로 한다. 명분의 개수로 고르지 않는다.
   - 컬러는 **프로젝트 브랜드**에서 가져온다.
6. **크리틱 루프** — §5를 따른다.

**구조층 패턴은 수용한다.** 탭 바·바텀시트·검색 같은 구조층 패턴은 그대로 써도 된다. 단 핵심 경험을 플랫폼 컴포넌트 조합만으로 끝내지는 않는다(core.md §7.3-5).

## 5. 크리틱 루프 — 시안을 좋게 만드는 곳

**B(본안)와 final은 최소 2회, A(대조군)는 1회** 돈다. B의 두 번째 루프 뒤에 명분·효익 표가 선택을 분명히 가르면 A는 멈춘다.

```
캡처 → 비평 → 가장 약한 3곳 수정 → 다시 캡처
```

**캡처**: `python3 scripts/shoot.py proto/B.html shots/B-r1`을 실행하면 화면마다 375×812 PNG가 나오고 콘솔 오류도 함께 보고된다.

- 조작 중인 상태(문항 3번째, 시트 열림, 오류)를 찍으려면 `--steps steps.json`을 쓴다. 형식은 `[{"go":"quiz"},{"click":"#opt-2"},{"wait":400},{"shot":"quiz-q3"}]` 같은 동작 목록이고, 자세한 설명은 스크립트 머리말에 있다. 캡처한 이미지를 **직접 본다.** Playwright가 없으면 설치하고, 그래도 안 되면 캡처 없이 코드를 검토하되 그 사실을 기록한다.

**비평은 디자이너의 눈으로 한다.** 묻는 것은 "규칙을 지켰는가"가 아니다. "이 화면이 좋은가, 무엇이 먼저 보이고 무엇이 거슬리는가"다. G7 항목으로 본다.

| # | 항목 | 보는 것 |
|---|---|---|
| ① | 위계 | 1순위 정보가 3초 안에 읽히는가. 주인공 화면에서 주인공이 무엇인지 즉시 알 수 있는가 |
| ② | 강조 | 강조점이 화면당 하나인가 |
| ③ | 균형·비율 | 무게가 한쪽으로 쏠리거나 비어 보이지 않는가 |
| ④ | 대비·리듬 | 평면적이거나 과하지 않은가. 반복이 지루하지 않은가 |
| ⑤ | 여백 | 근거 있는 여백인가, 정보가 부족한 여백인가 |
| ⑥ | 타이포 | 크기·굵기 위계, 본문 가독성, 한글 행간·자간, 한 줄 길이 |
| ⑦ | 디테일 | 빛·질감·모션이 의도를 갖는가, 그냥 많은가 |
| + | G3 | 뒤로 가기, 터치 타깃, 대비, 버튼이 버튼처럼 보이는가 |
| + | N7 | 1U·더프롬 형상·더프롬 컬러가 보이는가 |
| + | 효익 | 효익 지표가 화면에서 실제로 달성되는가. 설명 없이 3초 안에 되는가 |
| + | 담백/미완성 | 디테일을 뺀 곳마다 뺀 이유를 한 줄로 말할 수 있는가. 말할 수 없으면 비어 있는 것이다 |

**기록**은 회차마다 짧게 적는다. 본 것 3줄(G7 항목 번호), 고친 것 3줄, 남은 것.

## 6. 조형 기본기 — 프로토타입을 만들 때

- **`assets/proto-base.html`에서 시작한다.** 베이스에 들어 있는 것:
  - 1U 토큰
  - 판정 키트 모드(기본 / 무채색 와이어 / 정지 화면)
  - `go()` / `onEnter()` / 기기 뒤로 가기
  - 상단 바·스크롤 본문·하단 고정 바 구조
- **완성도 기준은 실제 출시되는 앱이다.** 와이어프레임이나 개념도가 아니다. 사용자가 이 화면을 받았을 때 "잘 만든 서비스"라고 느껴야 한다.
- **주인공 화면은 주인공답게 만든다.** 핵심 화면의 1순위 요소에 크기·여백·대비를 몰아준다. 정보를 균등하게 나열하면 도표가 된다.
- **효익이 보이게 만든다.** 결과가 글뿐이면 사용자는 읽어야 이해한다. 효익 시각화 표의 형식(`VIZ-*`)을 화면의 주요 요소로 쓴다. 인포그래픽이 장식이 되지 않도록, 각 시각화가 효익 지표 하나에 대응하게 한다.
- **서체를 먼저 확인한다.** 쓰려는 서체가 캡처 환경과 대상 기기에 실제로 있는지부터 확인한다. 예를 들어 한글 세리프는 기기 공통이 아니다. 없는 서체로 설계하면 루프 한 바퀴를 버린다.
- **타입**
  - 본문 2U 기준 스케일을 쓴다.
  - 한글은 행간 1.5 안팎, 제목은 자간을 약간 좁힌다.
  - 굵기 위계는 2~3단계로 제한한다.
  - 시스템 폰트를 대체로 썼다면 그 사실을 적는다.
- **컬러**
  - 60-30-10 비율을 지킨다. 강조색은 적게 쓸수록 강하다.
  - 채도가 높은 색을 여러 개 나란히 두면 도표나 장난감처럼 보인다.
- **모션은 성격 하나를 고른다**(`MOTION-*` 주 1개 + 보조 1개). 핵심 순간에 집중하고, 모든 곳을 움직이지 않는다.
- **장식에는 `data-decor`를 붙이고, JS 애니메이션은 `motionOK()`를 확인한다.** 그래야 G6 판정 모드가 작동한다.
- **실제로 작동하게 만든다.** 문항 → 결과 → 공유·공개 → 커뮤니티 → 입력까지 이어져야 한다. 목업 데이터는 그럴듯하게 채운다.
- **G3·N4를 지킨다.**
  - 터치 타깃 `--hit` 이상
  - 명도 대비 기준 충족
  - 초점 링 표시
  - DOM 순서를 의미 순서로 둔다(시각 배치는 CSS로)
- 외부 이미지 없이 SVG·CSS로 만든다.

## 9. 마무리 보고

짧게 알린다. 파일 내용을 대화에 옮겨 적지 않고 파일을 가리킨다.

1. 컨셉 한 문장, 메타포 한 문장
2. 화면별로 지킨 것 / 바꾼 것 / 사용자가 얻는 것 / 효익 지표를 한 줄씩
   - C 게이트에서 멈춘 경우에는 키트 위치와 go / 수정 / 중단 질문만 보고한다.
   - 브리프 게이트에서 멈춘 경우에는 빈 항목과 질문(최대 3개)만 보고한다.
3. A와 B의 명분·효익 표 요약 — 무엇이 개살구였고, 왜 B(또는 A)를 골랐는가
4. 크리틱 루프에서 가장 크게 나아진 점과 아직 약한 점
5. 게이트 현황. 예비 판정과 사람 판정 대기를 구분한다.
6. 사람이 할 일
   - 판정 키트 위치
   - 질문(최대 3개)
   - 틀리면 결과가 크게 바뀌는 가정
