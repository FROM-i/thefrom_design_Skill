# 브리프 — thefrom-ux

> ✎ **편집기로 쓰는 게 빠릅니다** — `tools/brief-editor.html`을 브라우저로 열면 칸마다 채우고, 게이트 판정과 모호한 표현 경고를 보면서 .md로 저장할 수 있습니다.

> **"더프롬처럼 만들어줘"로는 시작하지 않습니다.**
> 이 스킬은 감각을 흉내 내는 도구가 아니라 **판단을 대신 계산하는 도구**입니다. 판단에는 재료가 필요하고, 그 재료가 브리프입니다. 브리프가 부실하면 스킬은 빈칸을 가정으로 채우고, 가정 위에 쌓은 결과는 보기에는 그럴듯해도 틀린 방향으로 갑니다. 그 비용은 시안·시스템·실체화까지 전부 버려집니다.
>
> **★ 필수 6항목**이 비면 스킬은 S0에서 멈추고 질문부터 합니다(브리프 게이트). 나머지는 비워도 되지만, 채울수록 결과가 좋아집니다.

---

## ★1. 무엇을 — 서비스와 범위

| | |
|---|---|
| 서비스 한 줄 | |
| 이번에 만들 범위 | 화면 이름으로 (예: 진입·문항 / 결과 / 커뮤니티) |
| 핵심 흐름 | 사용자가 처음부터 끝까지 하는 일 (예: 동의 → 문항 8개 → 결과 → 공개 → 댓글) |

**왜** — 범위가 없으면 스킬이 화면을 지어내고, 지어낸 화면에 재해석을 합니다.
- 좋은 예: `토스 미니앱 성향 분석. 진입·결과·커뮤니티 3화면. 동의 → 8문항 → 결과 → 공개 승인 → 댓글`
- 나쁜 예: `성향 테스트 앱`

## ★2. 누구에게 — 타겟과 상황

| | |
|---|---|
| 누가 | 연령대 · 이 서비스를 알게 되는 경로 · 비슷한 서비스를 써본 정도 |
| 언제·어디서 | 어떤 순간에 여는가 (예: 송금 사이 1분, 퇴근길 지하철) |
| 기기 | 모바일 / 웹 / 키오스크 … |

**왜** — 타겟은 레이어 ①이고, 조형의 경계(가독성 하한·정보 밀도·톤의 폭)를 정합니다.
- 좋은 예: `토스를 매일 쓰는 20~30대. 송금·결제 사이 잠깐 들어옴. 성향 테스트는 여러 번 해봄`
- 나쁜 예: `MZ세대`

## ★3. 핵심 순간 — 사용자가 얻고 싶은 것

| | |
|---|---|
| 가장 중요한 화면 하나 | 이 서비스의 "주인공" 화면 |
| 그 순간 사용자가 원하는 것 | 이해하고 싶다 / 비교하고 싶다 / 자랑하고 싶다 / 결정하고 싶다 … |
| 지금 그 순간이 실패하는 지점 | 알고 있다면 (이탈·불만·흔한 비판) |

**왜** — 레이어 ③(동기와 감정)이고, 재해석의 `사용자가 얻는 것`과 효익 시각화가 여기서 나옵니다. 이 칸이 비면 결과는 **컨셉 아이디어에 머뭅니다**.
- 좋은 예: `결과 화면. "왜 이게 나야?"를 납득하고 싶다. 흔한 결과지는 유형명과 캐릭터만 있어서 납득이 안 된다`
- 나쁜 예: `결과가 예뻤으면`

## ★4. 브랜드 — 클라이언트(서비스)의 것

| | |
|---|---|
| 브랜드 컬러·서체·톤 | 가이드 첨부 또는 링크 |
| 모기업·플랫폼 브랜드를 따르는가 | |
| 없다면 | **`없음`이라고 적는다** — 서비스 약속과 타겟에서 새로 정합니다 |

**왜** — 레이어 ②입니다. 이 칸이 비면 공백을 메우려는 유혹이 생기는데, **더프롬의 컬러·1U 형상으로 채우는 것은 금지**(N7)입니다. `없음`은 판단이고, 빈칸은 판단하지 않은 것입니다.

## ★5. 제약 — 지켜야 할 것, 하면 안 되는 것

| | |
|---|---|
| 반드시 지킬 것 | 플랫폼 규격·검수·법적 고지·접근성 기준 … |
| 쓰면 안 되는 것 | 금지 표현·경쟁사 연상·특정 스타일 … |
| 재료 | 이미 정해진 것: 문항, 데이터 구조, 기존 화면, 카피 |

**왜** — 제약은 창의성을 줄이는 것이 아니라 **어디서 새로워질 수 있는지**를 알려줍니다. 문항·데이터가 이미 있다면 반드시 첨부하세요 — 없으면 스킬이 지어냅니다.

## ★6. 성공 기준 — 무엇이 되면 성공인가

| | |
|---|---|
| 이 작업이 끝났을 때 누가 무엇을 판단하나 | 예: 클라이언트 PT, 내부 방향 결정, 개발 착수 |
| 성공의 모습 | 관찰 가능한 문장으로 |
| 이번에 원하는 깊이 | C 게이트까지(방향만) / 끝까지(완성 프로토타입) |

**왜** — 성공 기준이 효익 지표의 출발점이고, 깊이가 비용을 정합니다. 기본은 **C 게이트에서 멈춤**입니다.
- 좋은 예: `클라이언트가 "결과 화면이 다른 테스트와 다르다"를 설명 없이 느낄 것. 이번엔 방향만 — C 게이트까지`
- 나쁜 예: `잘 나오면 됨`

---

## 7. 비교 대상 (권장)

경쟁·유사 서비스 2~3개와, 그중 **닮고 싶지 않은 것**. 링크나 캡처가 있으면 반대 대상의 실례가 되어 검색 비용이 줄어듭니다.

## 8. 판정자 (권장)

- G5 판정자: 이 프로젝트에 **참여하지 않는** 사내 3명
- 외부 타겟 판정자 (가능하면)

없으면 판정 키트까지만 만들고 판정은 보류됩니다.

## 9. 더 알려줄 것 (선택)

클라이언트의 성향, 지난 시안에서 거절된 이유, 절대 양보할 수 없는 한 가지.

## 예시 — 잘 쓴 브리프

```
★1 무엇을   토스 미니앱 '성향 분석'. 진입·문항 / 결과 / 커뮤니티 3화면.
            토스에서 성별·생년월일 제공 동의 → 8문항 → 결과 → 본인 승인 시 공개 → 댓글
★2 누구에게 토스를 매일 쓰는 20~30대. 송금·결제 사이 1~2분 틈. 성향 테스트 경험 많음. 모바일
★3 핵심 순간 결과 화면. "왜 이 결과가 나야?"를 납득하고 싶다.
            흔한 결과지는 유형명+캐릭터라 공유는 해도 납득은 안 됨
★4 브랜드   없음 — 새로 정함. 단 토스 앱 안에서 이질감이 과하면 안 됨
★5 제약     출시 목적 아님(TDS·검수 제약 없음). 생년월일은 공개 금지.
            문항 8개 초안 첨부
★6 성공     내부 방향 결정용. "다른 테스트와 다르다"를 설명 없이 느낄 것.
            이번엔 C 게이트까지
7 비교      16Personalities, 푸망 — 결과 카드 한 장으로 끝나는 방식은 피하고 싶음
8 판정자    디자인2팀 A, 기획팀 B, 개발팀 C (프로젝트 비참여)
```

## 예시 — 스킬이 멈추는 브리프

```
더프롬처럼 성향 테스트 앱 만들어줘. 트렌디하게.
```

→ ★1~★6이 모두 비어 있습니다. 스킬은 아무것도 만들지 않고 **브리프 인터뷰**(질문 최대 3개씩, 선택지 포함)부터 시작합니다.
